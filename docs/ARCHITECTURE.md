# MediaFlow-NAS 架构设计与系统原理 (Architecture Design)

本文档阐述 MediaFlow-NAS 的核心技术架构、双层存储模型、任务生命周期状态机、质量门禁决断机制与网络隔离拓扑。

---

## 一、双层存储分层模型 (Storage Tiering)

在家庭 NAS 中，直接将高并发写入落在大容量机械硬盘上会导致寻道噪音剧烈、响应缓慢，并且碎片化严重；而若全盘依赖 SSD，又受限于大容量 SSD 的高昂成本。

MediaFlow-NAS 采用标准的 **两层冷热存储分离架构 (Two-Tier Storage)**：

```text
┌─────────────────────────────────────────────────────────────┐
│ Tier 1: 高速热存储 (SSD 下载缓冲池)                         │
│ 路径: /volume1/迅雷/下载                                    │
│ 介质: NVMe / SATA SSD (高速并发写入、小文件分块校验)         │
│ 机制: 迅雷引擎实时写入分块 (.xltd)                          │
│ 保护: clean_ghost_dirs (8 重门槛安全修剪 0-entry 空目录)     │
│ 熔断: 低于 120GB 停投，高于 180GB 自动唤醒                   │
└─────────────────────────────────────────────────────────────┘
                              │ (任务完成校验 + <150MB 垃圾过滤)
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ Tier 2: 机械盘冷存储 (HDD 影视归档库)                       │
│ 路径: /volume2/video/avnook/#整理完成                        │
│ 介质: 机械硬盘 RAID 5 / Btrfs 存储池 (大容量、顺序读写)       │
│ 步骤:                                                       │
│   1. 顺序移入 #重刮队列 暂存区                              │
│   2. 累积满 3 部自动唤醒 JavSP 容器执行元数据抓取与转码     │
│   3. 最终移入规范归档目录: /#整理完成/{演员}/[{番号}] {标题}/│
└─────────────────────────────────────────────────────────────┘
```

## 二、任务生命周期状态机 (Task Lifecycle State Machine)

所有下载任务以 40 位标准小写十六进制 BTIH 作为全局唯一主键，受 SQLite 事务保护，状态机严格单向闭环演进：

```text
          [ 用户磁力输入 / 批量导入 ]
                       │
                       ▼
                    pending ──────┐ (新种 Tier-Fresh 优先准入)
                       │          │
                       ▼          │
                     active ◀─────┘ (动态水位调度: 保持 10~15 槽位)
                       │
         ┌─────────────┴─────────────┐
         │ (正常下载完成)            │ (0速度持续 3h / 元数据超时)
         ▼                           ▼
     completed                    stalled (移出物理槽位让位)
         │                           │
         │ (搬运+清洗+刮削+入库)      ▼
         │                         retry (按 6h/24h/72h 阶梯退避)
         ▼                           │
     archived ◀──────────────────────┘ (到期重新竞争活跃槽位)
         │
         ▼
     迅雷引擎任务 GC (释放引擎槽位，安全清理已完成记录)
```

### 状态机守恒公理 (Conservation Axiom)
数据库中任何维护、清理或优化操作，必须满足：
$$\text{Total}_{\text{after}} = \text{Total}_{\text{before}} + \text{Explicitly Imported} - \text{Explicitly Retired}$$
杜绝任何不可解释的任务丢弃或幽灵蒸发。

## 三、下载前智能质量门禁 (Pre-download Gate)

为了杜绝盲目下载、同质重复与无效流量，MediaFlow-NAS 设立了下载前质量门禁：

### 1. 媒体内容身份 vs 下载任务身份
* **BTIH (BitTorrent Info Hash)**：代表**下载任务身份**，用于物理查重与任务生命周期追踪。
* **Canonical AVID (规范番号)**：代表**媒体内容身份**（例如 `IPX-123`, `URE-131`, `CPZ-69015`），用于资产库查重与跨版本画质对比。

### 2. 真实多版本资产列表 (Multi-Profile Matching)
系统彻底废除将同一番号的多个存量文件合并为虚构“超级版本”的错误做法，而是在资产库中保留每个实际物理文件的独立 Profile：
* 只要本地存在一个真实文件**完全覆盖**候选资源的所有属性（分辨率、编码、内容、字幕）➔ 裁定 `SKIP`；
* 只要候选资源在任一维度具备**未被覆盖的新价值**（4K 升维、无码流出 UNC、中文字幕）➔ 裁定 `UPGRADE`；
* 候选信息模糊或存在取舍冲突 ➔ 裁定 `REVIEW`（默认不下载，人工可放行）。

### 3. HEVC 保护原则 (HEVC Protection Rule)
* **编码属于存储效率属性，而不是画质等级**。
* 严禁采用“新文件大小 > 旧文件大小 * 1.3”等简单粗暴的体积论。
* 当本地已存在 1080P HEVC 版本时，候选 1080P H.264 资源即便是 2~3 倍体积，亦判定为同档次冗余，坚决拦截，捍卫存储与带宽。

## 四、Emby 零负载单片叶子增量同步 (Zero-Load Sync)

传统影音自动化工具在完成影片入库后，往往直接触发 Emby Library Refresh：
* 这会导致 Emby 对整个大容量影视库（近 2 万部正片）发起全盘深度文件树递归比对；
* 机械硬盘磁头疯狂寻道，磁盘读写队列飙升，导致正在观影的客户端严重卡顿甚至假死。

MediaFlow-NAS 采用 Emby 原生专有的增量更新端点：
```http
POST /emby/Library/Media/Updated
Content-Type: application/json

{
  "Updates": [
    {
      "Path": "/volume2/video/avnook/#整理完成/演员名/[番号] 标题/正片.mp4",
      "UpdateType": "Created"
    }
  ]
}
```
* **单次耗时**：0.009 秒；
* **I/O 消耗**：精确访问该单个文件所在目录，零机械盘全盘寻道负担，入库即出墙，丝滑流畅。
